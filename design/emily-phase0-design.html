Emily — Phase 0 Design

Design v2 · the concrete blueprint for Phase 0 (“Foundation”) from the v1 design review · nothing here needs a Vapi account or phone number · everything is testable in the browser the day it’s built. Design only — no code has been written.
Phase 0 ships four things: the four Emily tables · the policy/decision REST endpoints under /api/emily/* · the Emily Console page · the Call Simulator. When Phase 1 adds the voice vendor, it plugs into these same endpoints — nothing gets rebuilt.

3 · API contracts — /MVPx/api/emily/*

All endpoints: JSON over POST · shared-secret header X-EMILY-KEY (env-configured, checked before anything else) · every request/response pair is archived to emily_events. These are the same six calls Vapi’s tools will make in Phase 1; the simulator calls them today.

EndpointInOut (always an explicit decision object)
/context{phone}{match:true, employeeId, name, route, staging, checkin:"07:42", paceAgeMin:4}
/rts-check{employeeId}{decision:"ALLOW"|"DENY"|"CLARIFY", rule:"RTS-01", say:"...", stops:"176/176", ageMin:4}
/log-exception{employeeId, category, count, inVan, attempts, note}{ok:true, incidentId:4412, say:"logged 2 damaged..."}
/rescue-candidates{employeeId}{decision:"RECOMMEND", candidates:[{helperId, score, paceGap, addedMin}], rule:"RSC-03"}
/escalate{callId, priority:"P1"|"P2", reason}{ok:true, transferTo:"+1...", say:"connecting you now"}
/call-complete{vapiCallId, employeeId, intent, outcome, confidence, durationSec, transcript, recordingUrl}{ok:true, callId}
Security recap: the Cloudflare tunnel (Phase 1) exposes only /MVPx/api/emily/*; the servlet rejects any request without the shared secret; no session, no cookies, no other MVPx URL reachable from outside. In Phase 0 nothing is exposed at all — the simulator calls the endpoints from inside the LAN.

4 · Data model — four new tables

CREATE TABLE emily_calls (
  CALLID INT AUTO_INCREMENT PRIMARY KEY, ENTITYID INT NOT NULL,
  VAPI_CALL_ID VARCHAR(64), EMPLOYEEID INT, PHONE VARCHAR(20),
  START_TIME DATETIME, END_TIME DATETIME, DURATION_SEC INT,
  INTENT VARCHAR(30), CONFIDENCE DECIMAL(4,2),
  OUTCOME VARCHAR(15),               -- resolved | escalated | callback
  TRANSCRIPT MEDIUMTEXT, RECORDING_URL VARCHAR(300),
  SIMULATED TINYINT DEFAULT 0,
  CREATE_USER VARCHAR(50), CREATE_DATE DATETIME, STATUS INT DEFAULT 0,
  KEY idx_emp (EMPLOYEEID), KEY idx_time (START_TIME)) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE emily_events (
  EVENTID INT AUTO_INCREMENT PRIMARY KEY, ENTITYID INT NOT NULL,
  CALLID INT, TOOL VARCHAR(30),      -- context|rts-check|log-exception|...
  RULE_ID VARCHAR(20),               -- RTS-01, RSC-03... the exact rule that fired
  DECISION VARCHAR(10),              -- ALLOW | DENY | CLARIFY | ESCALATE
  REQUEST_JSON TEXT, RESULT_JSON TEXT,
  CREATE_DATE DATETIME, STATUS INT DEFAULT 0, KEY idx_call (CALLID)) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE emily_escalations (
  ESCID INT AUTO_INCREMENT PRIMARY KEY, ENTITYID INT NOT NULL,
  CALLID INT, PRIORITY VARCHAR(2),   -- P1 | P2
  REASON VARCHAR(200), TRANSFERRED_TO VARCHAR(50), TRANSFER_SEC INT,
  RESOLUTION_STATUS VARCHAR(15) DEFAULT 'open',   -- open|handled|callback_done
  CREATE_DATE DATETIME, STATUS INT DEFAULT 0) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE rescue_assignment (
  RESCUEID INT AUTO_INCREMENT PRIMARY KEY, ENTITYID INT NOT NULL,
  CALLID INT, HELPER_EMPLOYEEID INT, TARGET_EMPLOYEEID INT,
  HELPER_ROUTE VARCHAR(20), TARGET_ROUTE VARCHAR(20),
  SCORE DECIMAL(4,2), PACE_GAP INT, ADDED_MIN INT,
  SOURCE VARCHAR(10) DEFAULT 'EMILY',             -- EMILY | DISPATCH
  ACCEPTED TINYINT, ASSIGNED_AT DATETIME, COMPLETED_AT DATETIME,
  RESCUE_STATUS VARCHAR(15) DEFAULT 'proposed',   -- proposed|approved|denied|done
  CREATE_USER VARCHAR(50), CREATE_DATE DATETIME, STATUS INT DEFAULT 0) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

Reused as-is: employee/contact (identity), route_assignment (today’s route), daily_itineraries (pace + freshness), dacheckin/dacheckout (on-road state), incidents (package exceptions land here with SOURCE=EMILY). Package-exception rows therefore appear on the existing MVPx Dashboard with zero extra work.

5 · Policy engine — deterministic rules & config

Plain Java, zero LLM. Every rule has an ID; the ID is what gets logged, displayed, and QA’d. Thresholds live in emily_config (simple name/value with audit), editable from the Config tab.

RuleCondition (all must hold)Result
RTS-01identity verified · stopsComplete ≥ RTS_MIN_PCT (default 100%) · itinerary age ≤ MAX_DATA_AGE_MIN (15) · driver not flagged as rescue helperALLOW — log + cleared script
RTS-02-STALEsame but itinerary age > limitDENY → P2 dispatcher confirm
RTS-03-SHORTstops below thresholdCLARIFY once → escalate
PKG-01identity verified · category ∈ {damaged, missort, OOT} · count ≤ PKG_MAX_COUNT (10)ALLOW — write incident
DEV-01device issue · ≤ 2 guided steps triedguide → re-ask “can you deliver?”
DEV-02-BLOCK“can you deliver?” = noESCALATE P2 route-blocking
RSC-03target behind pace ≥ RESCUE_MIN_GAP (10 stops) · helper window ≥ RESCUE_MIN_WINDOW (60 min) · both itineraries fresh · target not already in an open rescueRECOMMEND to console (Phase 4 flag: auto-assign)
EMR-01emergency keyword any time (accident, hurt, fire, robbery, “emergency”)WARM TRANSFER + P1 + SMS — never automated, not configurable
UNK-01unknown caller / no roster matchoffer dispatcher, never discuss route data
