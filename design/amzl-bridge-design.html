AMZL Bridge DESIGN v1 NOTHING BUILT YET

Goal: live itinerary data flows from logistics.amazon.com into MVPx continuously while a dispatcher has the portal open — no CSV exports, no Smart Upload step, no stale daily_itineraries. Freshness target: ≤ 2 minutes behind what the Amazon page shows (vs. hours/days today).

Why now: every consumer of daily_itineraries gets better the moment data is live — the MVPx Dashboard, Wave Sheet, Returns Board, and (paused, but next) Emily, whose RTS/rescue rules refuse to act on data older than MAX_DATA_AGE_MIN=15. Today that gate would deny almost everything; with the bridge it passes all day.

2 · Capture strategy — the key decision

A. DOM scrapingB. Network tap (recommended)C. Replay Amazon APIs ourselves
How Read the rendered table cells off the page Wrap window.fetch/XMLHttpRequest in the page world; copy the JSON responses the page already received Background worker calls Amazon endpoints directly using the session cookies
Data qualityOnly what's visible; breaks on any CSS change; pagination pain Full payload incl. fields the UI hides (pace, projected return, IDs)Full payload
Extra load on AmazonNoneNone — zero additional requestsNew synthetic traffic, detectable, ToS-hostile
FragilityHigh (UI markup)Low (API shapes change rarely; raw staging lets us re-parse)Medium + risk of auth challenges/captchas
VerdictFallback only ("Capture visible table" button)Default — passive, invisible, zero footprintRejected
Compliance stance: the bridge is passive. It never logs in, never stores Amazon credentials, never fires its own requests at Amazon — it only copies JSON the dispatcher's own browsing already fetched, for the DSP's own operational data. Active auto-polling (option C) is explicitly rejected. If we later want fresher data than natural browsing provides, the opt-in "assisted refresh" (§6) drives the page's own refresh control at a human cadence (2–5 min) in the open tab — still visible, still session-bound, still rate-limited. Amazon has been hostile to scraping tools before; passive capture of your own portal session is the defensible end of the spectrum.

3 · Chrome extension (Manifest V3)

PieceResponsibility
manifest.jsonMV3. host_permissions: https://logistics.amazon.com/* + http://localhost:8080/* (configurable base). Permissions: storage, alarms, scripting. Loaded unpacked (internal tool — no Web Store review needed).
tap.js (page world)Wraps fetch + XMLHttpRequest. URL allow-list (configurable regexes, e.g. anything under /operations/ returning JSON). Posts {url, ts, status, body} to the content script via postMessage. Never touches request sending — read-only on responses.
content.jsInjects tap.js, relays captures to the service worker, draws a tiny status chip (● LIVE / ● OFFLINE) on the portal page.
sw.js (service worker)The brains: parser registry keyed by URL pattern + parserVersion; normalizes itinerary payloads to rows; SHA-256 hash per payload → skip unchanged; per-row diff → only changed rows pushed; outbound queue in chrome.storage.local with exponential backoff (MVPx down ≠ data lost); 60s heartbeat via chrome.alarms.
popup.htmlStatus: Amazon session OK? last capture age, rows pushed today, MVPx reachable, queue depth. Controls: on/off, MVPx URL + ingest key, serviceAreaId→station map, "Capture visible table now" (DOM fallback), "Send last raw payload" (debug).

New IngestApiServlet at /api/ingest/* — same shared-key pattern as the Emily API (key lives in emily_config-style table or reuses it; 401 otherwise). LAN-only, never exposed through any tunnel.

TablePurpose
amzl_raw newEvery captured payload verbatim (url, hash, capturedAt, body MEDIUMTEXT). This is the safety net: when Amazon changes a field name, history is re-parsable — fix the parser, replay the raw rows, no data lost. Pruned after ~14 days.
ingest_log newOne row per push: source, rowsIn, rowsUpserted, parserVersion, outcome, ms. Feeds the bridge-health panel.
daily_itineraries (existing)UPSERT in place keyed on (TRANSPORTERID, DATE(ITINARARYDATE)) — update stops/progress/pace + UPDATE_DATE=NOW(), insert if new. No delete-and-reload: row IDs stay stable, and UPDATE_DATE is exactly the freshness signal Emily's MAX_DATA_AGE_MIN gate reads. Bridge writes win over Smart Upload for the same key (same-day file uploads become redundant, not conflicting).

4b · Second leg: Slack wave-sheet images REVISED 07/16

Wave sheets arrive as images posted in a Slack channel — but the workspace is Amazon's Slack, where the user is only a member. That rules out the normal Slack-app/bot-token route entirely: installing any app (bot or user token) requires workspace admin approval, i.e. Amazon's. So Slack becomes a capture target of the same Chrome extension — identical passive posture as the portal pages.

StageWhat happensWhere
W1 — CaptureExtension gains app.slack.com host permission. When the dispatcher has Slack open in Chrome (web client, not the desktop app) and the wave-sheet channel is viewed, the tap captures the channel-history JSON; for new image posts the content script fetches the full-size file through the browser's own logged-in session (one request per image — the same fetch clicking the image would make). Image + metadata (channel, ts, poster, hash) POST to /api/ingest/slack-wavesheet → stored in MVPx docs + slack_wavesheet row. Wave Sheet page shows the latest sheet.Extension
W1-alt — Drop zone always availableA drag-and-drop target on the MVPx Wave Sheet page: drag the image straight out of Slack (desktop app or web) onto the page. Same ingest path, zero extension dependency — this is the fallback when nobody has Slack open in Chrome.MVPx page
W2 — Extract phase 2Vision model (Claude API) parses the image into structured wave rows (wave time, route, DA, staging) → lands in the same tables the Wave Sheet page reads, flagged SOURCE='SLACK' with a confidence score; low-confidence rows queue for one-click human confirm. Extracted rows never overwrite manually-entered data without confirmation.Java → Claude API

Open decisions: W-a: which channel (name)? W-b: display-only first, or straight to extraction? W-d: is opening Slack in Chrome acceptable for whoever watches that channel? (If everyone insists on the desktop app, the drop zone alone still removes the save-file-then-upload dance.)

Posture note: same passive rules as the portal capture — content the member can already see, read from their own logged-in browser tab, no bots, no stored credentials, no synthetic polling of Slack. The free-membership 90-day history limit doesn't matter: images are archived into MVPx within minutes of being seen, giving you a permanent wave-sheet archive Amazon's free membership doesn't.
